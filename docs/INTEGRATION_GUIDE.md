# 新工具接入流程

开始导入前，按内容政策配置仓库外私有词库；规则本身不得进入工具或仓库。所有下述完整校验均需加载该配置，不能以 `--structure-only` 替代；对外报告不附命中原文或敏感路径。

用户提供原始文件或位置即可，协作者自主整理，不要求用户先满足目录或命名规范。整理责任与接收区约定见 [启动材料与工具交付清单](INTAKE_CHECKLIST.md)。实际填写的私有交付说明留在仓库外，不随工具导入。

## 0. 接收与隔离

从仓库外的临时目录接收原始 HTML 和资源。先清点文件、许可、外链、依赖、功能与可能的敏感内容。不能原样先 commit 再清理；公开 Git 历史会保留旧版本。

## 1. 清理

对文本、路径和图片可见内容做人工与程序双检。替换非功能性旧名称为 DPG 或中性词；同步修正引用。固定第三方协议字段可能不能改，若含不允许的内容或无法确认来源，则阻断而不是硬替换。去除跟踪、内部地址、调试内容和无关数据。把清理后的版本复制到 `tools/<slug>/`，立即补齐初始 `draft` 的 `tool.json` 后运行校验。

## 2. 视觉与功能

记录原工具可操作流程、预期结果和核心视觉。按 `DESIGN_SYSTEM.md` 更新文字层级、控件、参数区、边框与响应式。保持工具特有画面。分别检查主操作、异常输入、重置、键盘、触屏及缩小动效，确认没有破坏原功能。

## 3. 元数据与索引

写 `tool.json`，初始 `draft`。完成自测改 `review`，评审通过改 `ready`。在准备发布的同一变更中改为 `published` 并加入 `tools.json`。运行 `node scripts/verify.mjs`；再生成站点并在本地预览。

## 4. 发布验证

检查全部工具列表、空状态、站内 iframe、独立打开、浏览器后退、移动端及 Pages 仓库子路径。检查控制台、网络失败和资源 404。执行 `git diff --check`，按 QA 清单逐项确认。在功能分支创建本地提交，按 GitHub 工作流先做风险检查，再取得本次推送确认；PR 合并与版本发布另行明确授权。未来 Pages 工作流仅部署已批准的版本标签，记录网址、版本、commit 和 Action 结果。

## 5. 更新与回退

更新只修改对应工具目录、必要元数据和构建逻辑；`updated` 与版本同步。阶段性提交信息如 `feat(tool): add color grid`、`fix(tool): repair mobile controls`。若上线后故障，优先用新的修复提交或 revert 恢复，不改写公开历史；回退也须经过风险检查和明确授权，以新版本记录回退对象，再观察 Pages 部署结果。
