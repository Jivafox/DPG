# GitHub 版本管理与 Pages 发布

## 授权边界

本地阅读、修改、校验、差异审查和功能分支上的本地提交可按任务推进。每次 push 必须先完成风险检查，再取得用户对本次操作的明确确认；历史授权、具备凭据或一般“继续”不构成下一次 push 的授权。确认仅覆盖已展示的远端、分支/标签、精确 commit 和操作；内容、目标或部署影响变化时重新检查并确认。纯网络失败且内容与目标未变，可在同次授权范围内重试。

推送开发分支、创建 PR、合并 PR、推送发布标签和上线是不同操作。开发分支 push 授权不包含合并或发布；后续外部写入也需明确说明并获得对应授权。一次确认可以覆盖明确列出的操作组合，但不能覆盖尚未知晓的合并 commit 或未来修改。未确认时保留本地成果，报告“待确认、未推送”，不因等待确认撤销成果。

## 分支与版本

- `main` 为经过审核和 CI 验证的稳定集成分支。每个阶段从适当基线建立 `feat/<topic>`、`fix/<topic>` 或 `docs/<topic>`，通过 PR 合并；单人工作也遵循该方式，不直接在 main 开发或推送 main。
- 每个有意义的本地提交使用可读信息，如 `docs: simplify first release scope`。提交 SHA 识别开发快照，PR 记录变更目的与验证证据。禁止强推和改写共享历史。
- 每个验收后的稳定阶段创建附注标签，统一使用 `vMAJOR.MINOR.PATCH`；首次稳定规范基线可用 `v0.1.0`。增加能力提升 MINOR，修复或文档修订提升 PATCH；不兼容变更提升 MAJOR。版本号须检查现有标签后确定，不能重复使用或移动旧标签。
- 每个稳定版本在 `docs/releases/<version>.md` 留下记录：版本、日期、类型（规范/站点）、变更、关联 PR、验证结果、风险与回退目标。该记录随版本进入 Git；标签指向精确发布提交，GitHub Release 补记该 SHA、标签、PR、部署运行链接和状态。规范版本无站点部署时明确写“不适用”。
- 工具 `tool.json.version` 识别单个工具变更，与整个项目的版本标签独立；更新工具时同步版本及 updated。

## 标准流程

1. 查看工作区、分支、远端及基线，保护未提交工作。在功能分支完成本地成果及相关验证；计划形成稳定版本时，将版本记录一并纳入该分支（实际合并 SHA 与部署结果后填到 Release）。规范阶段不要求构建不存在的网站。
2. 精确暂存并审阅完整 diff，创建本地 commit；执行下面的风险检查。发现阻断项先修复，不请求带阻断项的推送批准。
3. 向用户展示检查结论、完整 commit SHA、准确远端、分支、变更概要、公开范围、自动任务影响和回退方式，请求本次 push 确认。默认使用明确的 ref，不使用 `--all`、`--mirror` 或批量推送所有标签。
4. 确认后 push；如获授权创建 PR，等待 CI 并审阅结果。合并前向用户展示 PR、精确 head/base SHA 与检查状态，确认后才合并；任一 SHA 改变需重新审阅。推荐 merge commit，保留分支提交与合并边界。
5. 合并后读取实际 main commit，核对随提交合入的版本记录并准备版本标签；若记录需要修改，另走功能分支与 PR，不直接改 main。明确展示标签与 commit、是否上线，再取得本次发布操作确认。推送标签和创建 Release 均限于已确认对象。
6. 检查远端结果，记录分支、commit、PR、版本、CI 和部署状态。站点部署成功后实际访问公开网址才报告已上线；推送成功不等于上线成功。

## 确认前风险检查

- 内容：审查本次新增公开的源码、文档、资源、提交历史、文件名、图片、外链和依赖；不含秘密、个人或内部资料；许可与必要署名完整。草稿源码也在公开范围内。
- 自动门禁：先人工确认仓库外私有词库完整可用，确认规则本身未以明文、编码或衍生信息进入拟公开内容；运行 `node scripts/verify.mjs`；有 Git 历史后运行 `node scripts/verify.mjs --history`；运行 `git diff --check` 和 `git diff --cached --check`，并审阅将要推送的提交差异。首次推送审查全部拟公开内容。公开 CI 绿色不能代替本地完整内容检查；对实际合并后的 commit 和拟发布标签也须在本地补做完整检查，绑定准确 SHA 后才能批准上线。
- 功能：按本次范围完成 QA；有页面时实际检查交互、响应式、资源路径与控制台。有构建时确认只输出已批准公开文件。
- Git：确认准确远端、当前远端状态、分支/标签、提交范围、未提交文件、冲突和保护规则；不混入无关改动。提交后再次确认被批准的文件没有变化。
- 自动化：审查本次实际 workflow、权限、触发条件及其变更，说明 push 是否可能触发发布；不能仅依赖本文约定推断真实配置。
- 回退：明确上一稳定标签、目标 commit 和恢复步骤；首版没有上一版本时明确说明，只能撤下站点或后续修复。

私有规则扫描不是完整的密钥、版权或隐私检测。检查失败或公开范围不明时停止外部写入；先保留本地成果并说明问题。

## 首次连接与远端配置

目录尚未初始化 Git 时，不虚构分支、commit 或历史检查结果。拿到准确仓库 URL 后检查已有远端内容再选择初始化、克隆或合并策略；不擅自覆盖已有历史。凭据使用现有授权，不写入项目。首次 push 仍须完整风险检查与明确确认。全新空远端若必须先建立 main 基线，应作为一次明确标注的初始化例外，展示全部基线内容和 commit，经用户专项确认后执行；之后所有开发遵循功能分支与 PR 流程。

远端计划配置 main 保护、PR 审核、禁止强推及必需 CI 检查；实际检查名称从 Actions 运行结果读取。是否具备所需设置权限和仓库支持情况，首次接入时核实；未配置的保护不得宣称已生效。可设置 `git config core.hooksPath .githooks`，但 hook 与文档均不能强制保证用户授权。

## 自动化边界

`.github/workflows/validate.yml` 在 push 和 PR 时进行通用结构检查、Node 测试和结构模式构建，不接收私有词库或执行私有历史扫描。`.github/workflows/pages.yml` 仅由 `v*` 标签触发，检出该标签精确 commit，并校验、构建、部署同一版本。部署前验证标签属于已审核 main 历史且版本记录类型为站点；规范版本只验证，不部署。

未来启用 Pages 的 GitHub Actions 来源，部署 job 仅使用所需权限，上传 dist 站点产物而非整个仓库。main 合并不自动上线；设置手动重跑或其他发布入口时，同样遵守上线授权规则。首次上线前实测触发条件、子路径、构建产物和回退流程。

## 回退与失败

通过标签和发布记录定位上一稳定版本，从当前 main 建立 `fix/rollback-<version>`，用新的 revert 或恢复提交撤销有问题的变更，保留版本记录并重新验证；按相同风险检查、确认、PR 和版本发布流程上线新版本。回退记录注明被撤回版本、恢复目标与原因，不移动旧标签、不 reset/强推 main。

若上游改变，先 fetch 并审查、整合变化，重新校验；提交或目标改变后重新请求确认。认证或 CI 失败时保留本地成果并报告，不绕过检查。敏感信息事件按内容政策处理，普通 revert 不能清除历史中的内容。
