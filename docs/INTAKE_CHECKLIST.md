# 启动材料与工具交付清单

本文件是公开通用模板，不填写本机绝对路径、私有来源、账号信息或敏感原文。实际工具交付说明保存在仓库外，与原始文件一起接收；只将审核后的公开描述写入工具元数据。提供材料不代表授权推送或上线。

## 用户只需提供原始材料

提供已有文件、压缩包、文件夹或其本地位置即可，保留现有名称和目录结构。无需预先改名、解压、分类、识别入口、填写说明模板或制作元数据。若知道必须保留的效果，可以顺带说明；这不是接收前提。

工具名称、用途、入口、运行方式、依赖、权限需求与典型操作由协作者先从文件和实际运行中识别并记录。只有缺少必要资源、多个版本无法判断、核心行为含糊或公开许可无法核实时，才提出具体问题；同时继续不受影响的整理工作，不要求用户重做整份材料。

GitHub 仓库地址在连接时提供即可；没有仓库不影响接收检查或页面草图。项目自身许可在首次公开前确定，不因文件已交付就推断拥有公开授权。

默认延续 DPG 名称、V2 中性深色与白色高亮、全部工具响应式网格平铺、点击进入运行页；首页使用 Design Playground 标题与英文简介，工具说明沿用现有语言。只有希望修改时才补充意见。分类、搜索、筛选、工具封面和自定义域名不是启动前提。

首次公开前另行确定项目自身开源许可、仓库权限与保护设置、发布版本及回退目标。不需要现在准备所有后续工具。

## 原始归档放在哪里

现有文件在仓库外时，直接提供当前位置即可，不要求用户搬动。需要统一收纳时，由协作者在本机用户主目录创建 `~/DPG-Inbox/`，作为私有接收区；`~` 表示用户主目录。这是推荐路径，不表示目录已经创建。它必须位于 DPG 仓库外，也不要初始化成公开仓库或放在自动云同步位置。检查其真实路径，避免通过软链接实际落入项目。

不要把原始归档放进 DPG 的 tools、docs、assets、dist 或任何其他子目录；即使加入 .gitignore 也不作为隔离方案。私有词库继续留在原有用户级配置目录，不放进归档或交付包。

以下是协作者整理工作副本时可采用的结构，不要求用户准备：

```text
DPG-Inbox/
└─ color-grid-2026-09-28-r01/
   ├─ source.zip          # 原始归档；也可换成 source/ 文件夹
   ├─ intake.md           # 私有交付说明，模板见下文
   └─ reference.png       # 可选：脱敏后的效果参考
```

接入时保留原件，在接收区的独立工作副本中解压、检查和清理；原件和私有说明不直接复制到项目。只把通过检查的运行文件和必要许可文件导入 `tools/<slug>/`，再补齐 tool.json。

## 协作者如何命名

交付目录采用 `<slug>-<YYYY-MM-DD>-r<序号>`，如 `color-grid-2026-09-28-r01`；同一天补交使用 r02，不覆盖上一份。slug 使用小写英文、数字和连字符，描述功能，不含个人、组织或来源身份。交付序号仅用于区分收到的材料，不是正式发布版本。

如果直接交付一个 ZIP，可命名为 `color-grid-2026-09-28-r01.zip`。现有文件已经命名也没关系，只需提供文件或位置，入口由协作者识别；不要为了命名规范批量修改内部文件而破坏资源引用。最终导入时再统一入口、目录和引用。

## 协作者负责的整理工作

1. 保留用户原件，在仓库外建立工作副本。先检查归档文件清单、展开体积、越界路径和符号链接，再处理文件；不自动运行未知安装脚本。
2. 清点各工具与版本，识别 HTML 入口、资源引用、构建配置和依赖关系。支持单文件 HTML、完整源码文件夹或可读取的归档；归档格式无法读取时明确说明缺少的能力。
3. 自主拟定中性 slug、显示名称与用途描述，整理目录及相对资源路径。修复引用时保留核心交互，不要求用户先整理成 index.html/assets 的结构。
4. 检查代码、素材、图片文字、元数据、外链及许可；清理旧身份与敏感内容，隔离凭据、历史、缓存和无关数据。必要许可证与署名保留，许可不明时暂停相关内容导入。
5. 识别启动与构建方式、CDN、外部 API、服务端依赖及权限需求；评估纯静态 V1 的适配。缺失凭据时不索取密钥，先评估能否去除依赖或使用可公开替代方案。
6. 使用可公开的虚构输入记录核心流程与结果，生成私有整理记录。只有文件中无法判断的关键缺口才向用户询问；不编造依赖、授权或测试结论。
7. 清理通过后导入独立工具目录，补齐 tool.json、版本与状态，按设计系统适配并完成校验和实际走查。

用户不需要提前制作工具说明、封面、截图或统一界面。已有参考资料可一并提供；无需为交付补齐所有可选材料。私有词库不放入交付包。

## 提交材料后的处理顺序

接收与清点 → 仓库外检查及清理 → 记录核心交互 → 导入独立工具目录并填写 draft 元数据 → 私有词库和结构校验 → UI 适配及实际操作检查 → 本地验收 → 风险检查与具体推送确认。

工具代码、资源和许可通过审核前，不进入 Git 工作树。用户提供文件或允许接入，不等于授权 push、合并或上线。
